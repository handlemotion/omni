# 0007: Reply lanes judge both directions

Date: 2026-11-03 · Status: accepted · Amends: spec v1 "Triage", ADR 0002

## Context

The spec files a thread whose latest message is ours as `waiting_on_them` without a model call
(`docs/spec/v1.md`, "Triage"), and ADR 0002 kept that rule ahead of Jev. That rule is wrong half
the time: a reader's "thanks!", "sounds good" or "here's the file" ends a conversation, yet it put
the thread in Awaiting reply, where it sat forever.

The lanes, from the reader's point of view:

- **Needs reply** (`needs_reply`): someone else wrote last and is waiting on the reader.
- **Awaiting reply** (`waiting_on_them`): the other side owes the reader something. Usually the
  reader wrote last and asked for something: an answer, a file, a decision.
- Neither: a closer, an FYI either side sent, or a message that asks nothing.

A second gap: a person's re-sort (`triage_source = 'person'`) was final forever, so a reply on a
re-sorted thread never moved it between lanes.

## Decision

**Who wrote last is a fact; whether they asked for something is a judgment.** Code picks the
question set from the fact, and Jev answers only the judgment (`packages/ai/src/questions.ts`):

- Someone else wrote last: the existing five questions and truth table (`TRIAGE_TABLE`).
  `needs_reply` exists only in this table, so it can only fire when someone other than the reader
  wrote last.
- The reader wrote last: three Nouls over a state framed as the reader's own message (no sender,
  no list headers, the two newest earlier messages for context):
  `reader_asks_question` ("Does `latest_message` ask its recipients a question they need to
  answer?"), `reader_requests_action` ("…ask its recipients to send or do something?") and
  `sent_by_system` ("…generated by software rather than written by a person?"). A person's ask
  either way → `waiting_on_them`; software-sent → `fyi`; nothing asked → `fyi`; a deciding
  judgment between the bands → Unsure (`SENT_TABLE`). Two ask questions rather than one
  "response or action", per the one-judgment rule. `sent_by_system` exists because the live run
  filed our own magic-link email ("Open this link to sign in") as Awaiting reply at 0.97: it
  does ask for an action, but nobody waits on it.
- **Reader closers go to `fyi`**, not `noise`: the thread is a real conversation the reader may
  want to find and summarize; it just asks nothing of anyone.
- On Claude, the reader-sent case uses the same framing and an output schema of
  `waiting_on_them | fyi`, so it cannot return `needs_reply` either.
- The only model-free path left is a reply from the reader with no letters or digits (empty, a
  lone 👍, attachment only) → `fyi`, confidence 1. A first message is left to the model, since
  its subject may carry the ask. Without any AI key, other reader-sent threads stay unsorted
  instead of being guessed into Awaiting reply.
- An inbound "I'll get back to you next week" still files as `waiting_on_them` (ADR 0002's
  `promises_follow_up` row). The reader didn't write last, but they are waiting on the other side,
  which is what the lane is for.

**The triage describes the thread's latest message.** New column `threads.triage_message_id`
(additive migration `0004_triage_message_id`) records which message the stored triage was made
on:

- A queue job for a message already triaged (a redelivery, or a retry after the summary failed)
  reuses the stored triage: no model call, outcome `done_already`. Before, a job without a
  summary re-ran the model every time.
- A new message from either side re-triages the thread, **including after a person's re-sort**.
  A re-sort holds until new mail arrives. The re-sort route (not built yet) must set
  `triage_message_id` to the latest message it was made on.
- `saveTriage` writes only while its message is still the thread's latest (same `sent_at, id`
  order as `loadThreadForAi`), so a slow job can't overwrite a newer message's triage
  (outcome `superseded`).

**`TYPESAFE_API_URL`** (optional, default `https://api.typesafe.ai`) points the Worker at a
TypeSafe endpoint. Self-hosters can use it for a proxy; the e2e suite uses it for replay.

## Evidence

- `fixtures/eml/triage-*.eml`: a four-message thread (inbound request → reader's question →
  inbound answer that asks back → reader's "thanks!") plus an inbound FYI and an automated
  receipt. `fixtures/triage/recordings/` holds Jev's live answers to the exact requests
  (`pnpm --filter @omni/ai record`). On `jev-1.14.0`: needs_reply 0.99, waiting_on_them 0.98,
  needs_reply 0.99, fyi 0.97 (asks 0.02, requests 0.03, software 0.01), FYI 0.86, receipt fyi
  0.98. Live answers vary by a few points between calls (the FYI scored 0.82 to 0.88 across
  runs), so a case near 0.85 can land in Unsure; it never enters a reply lane.
- The opt-in eval (`pnpm --filter @omni/ai eval`) gained seven reader-sent cases written before
  any tuning (offer-to-help closer, confirming a time, promising to send, sending the file,
  asking for a review, a yes/no question, thanks plus a question) and a sign-in link sent from
  our own mailbox: all correct and auto-filed on Jev. The question wording was not tuned to them.
- `apps/worker/e2e/triage-lanes.e2e.test.ts` runs the thread through GreenMail, the real mail
  service, Postgres and the Worker, and reads each lane back from `/api/threads?lane=`. TypeSafe
  is replaced by an HTTP server that serves the recordings and refuses any other request, so CI
  never calls a live model and a change to the questions or state fails until re-recorded.

## Risks

- One recorded thread is a small sample. The reader-sent questions should join the measurement
  in ADR 0002 (re-sorts out of Awaiting reply and FYI) once `triage_feedback` has data.
- Reader-sent threads now cost a Jev call each (about $0.00004) where the rule was free.
- A thread a person re-sorted moves again on new mail. If people expect re-sorts to stick to the
  thread, the rule becomes "re-triage only if the new message is from the other side".
