# Omnidirectional: v1 spec

Oct 31, 2026 · @Rodrigo Jiménez

## Summary

Omnidirectional is one AI-first inbox for every domain Rodrigo's projects and companies use. It reads mail as conversations, summarizes them, and sorts what needs a reply.

The bet: email hosting is a commodity. We rent it from Purelymail and spend our effort on the experience. Purelymail stores, filters and delivers mail. Omnidirectional is the window on top.

v1 is internal, for Rodrigo's teams, on web and iPhone. It is built to become a SaaS (software sold as a subscription) later. Every decision below either already supports that, or names what changes when we get there.

## Principles

- Use maintained libraries for email protocols, auth and parsing. Write our own code only where the product is different: threading, rendering and AI.
- Mail passwords live in one service and nowhere else.
- Purelymail is the source of truth for mail. Our database is an index we can rebuild.
- Every background job is safe to run twice.
- Every row carries an `org_id` from day one, so serving customers is a product change, not a rewrite.
- When an idea needs a workaround for odd conditions, pick the standard, boring path instead.

## Goals and non-goals

v1 succeeds when Rodrigo's team runs all project email through Omnidirectional on web and iPhone, and Apple Mail is only a fallback.

**Goals**

- Every inbox across every domain in one place, on web and iOS.
- Personal inboxes, plus shared inboxes like hello@ that several people can see.
- Conversations shown as message threads, with quoted history stripped.
- An AI summary at the top of every thread.
- AI triage that sorts threads into needs reply, waiting, FYI and noise.
- Search across all mail.
- New mail shows up within a few seconds.
- Total infra cost under $25 a month for the whole team.

**Non-goals for v1**

- Running our own mail server. Purelymail does that.
- Outside customers, billing, or self-serve signup. The data model is ready for them, the product is not.
- Connecting Gmail or Microsoft 365 accounts. Planned for SaaS.
- Drafted replies and "ask your inbox" chat. Both are good v2 candidates.
- Calendar, contacts, or file storage.
- Android.

## Glossary

| Term | What it means here |
| --- | --- |
| IMAP | Internet Message Access Protocol. How an app reads mail stored on a server: folders, flags, read state. |
| IMAP IDLE | An IMAP mode where the server tells an open connection about new mail right away, so nothing has to poll. |
| CONDSTORE | An IMAP extension that returns only what changed since the last sync. |
| UID, UIDVALIDITY | A message's number inside one IMAP folder, and a folder value that changes if those numbers get reset. |
| MODSEQ | IMAP's change counter. Higher means newer. |
| SMTP | Simple Mail Transfer Protocol. How an app sends mail. |
| MX record | Mail Exchange. The DNS setting that says which server receives mail for a domain. |
| SPF, DKIM, DMARC | DNS records that prove mail really came from your domain. Without them, mail lands in spam. |
| MIME | The raw format of an email, including body parts and attachments. |
| App password | A separate password for one app on one mailbox. It can be revoked without touching the real password. |
| Postgres | A widely used open-source SQL database. |
| Hyperdrive | Cloudflare's connection pool that lets Workers talk to Postgres quickly. |
| R2 | Cloudflare's file storage. |
| Durable Object | A Cloudflare Worker with its own storage that can hold live connections, like websockets. |
| APNs | Apple Push Notification service. How iOS apps get notifications. |
| SPA | Single-page app. The browser loads the app once and talks to the API from then on. |
| SaaS | Software as a service. Sold to customers as a subscription. |
| Multi-tenant | One system serving many separate customers, each seeing only their own data. |
| Outbox | A database table of actions waiting to happen. A worker reads it and carries them out, retrying on failure. |
| Idempotent | Safe to run more than once. Running it twice gives the same result as once. |
| Dead-letter queue | Where jobs go after failing too many times, so they can be inspected instead of lost. |
| Thread | A conversation: an original email plus all replies. |
| Triage | Sorting a thread into a bucket like needs reply or FYI. |

## Architecture

The system has two halves. A small always-on mail service owns every conversation with Purelymail. Cloudflare Workers own everything people touch: the API, AI jobs and live updates. Both halves share one Postgres database.

&#91;embedded content: Omnidirectional architecture · mail service, Workers, storage\]

New mail flows left to right along the top. The mail service is the only part that holds mail passwords. Workers never talk to Purelymail directly.

### Hosting: Purelymail

- One Purelymail account, about $10 a year at our usage. Unlimited domains, users and storage.
- Each person gets a Purelymail user. Each shared inbox (hello@, billing@) is also a Purelymail user.
- Purelymail handles spam filtering, DKIM signing, deliverability and storage. Apple Mail keeps working on every account as a fallback.
- The Purelymail API automates setup: domains, users and app passwords. Only the mail service calls it.

### Mail service

One small Node app on one always-on Fly.io machine. It is the only code that speaks IMAP or SMTP.

- Built on ImapFlow (IMAP), Nodemailer (SMTP) and mailparser (MIME). All three come from the same maintainer and are widely used.
- Holds one IDLE connection per mailbox on the inbox, so new mail arrives in about a second.
- Every 5 minutes, syncs the other folders using CONDSTORE. This also picks up changes made in Apple Mail.
- On new mail: parse it, strip quotes, assign a thread, save the raw file to R2, save the index to Postgres. Then call the API Worker so it can queue AI jobs and notify open apps.
- Carries out user actions from the outbox: send, archive, move, mark read.
- First-time history import runs here too, the first time a mailbox is added. No separate script.
- Its only route is one private endpoint. Calls must carry a signature (HMAC) and a recent timestamp.

### Workers

One Worker, one deploy. It holds the Hono API, the web app's files, the queue consumer for AI, and the realtime Durable Object. One config file, one set of bindings.

- The API checks login with Better Auth and reads Postgres through Hyperdrive.
- The queue consumer runs triage and summaries, then writes results to Postgres.
- The Durable Object keeps one websocket per open app and sends Expo push notifications to phones. Apps refresh what changed instead of polling.

### Actions: the outbox

When someone archives, marks read or sends, the API writes a row to `mail_actions` and pings the mail service. The mail service performs the action on IMAP or SMTP and marks the row done. It also checks the table every 30 seconds, so a lost ping only delays an action.

- The app updates instantly. It does not wait for Purelymail.
- Failed actions retry with backoff and show an error after the last attempt.
- Every send carries an idempotency key, so a retry never sends the same email twice.

### Sending

- Nodemailer sends through Purelymail's SMTP.
- Replies set the `In-Reply-To` and `References` headers so they thread correctly everywhere.
- SMTP does not file a copy in Sent. The mail service appends one over IMAP, so Apple Mail stays in sync.
- The sent message is saved to Postgres right away, so it appears in the thread immediately.

### Sync rules: who wins

- Purelymail is the source of truth. If Postgres is lost, a full re-sync rebuilds it.
- Personal mailboxes: read, archive and move sync both ways with IMAP. The newer change wins, judged by MODSEQ.
- Shared mailboxes: read state is per person and lives only in Postgres. We never change the IMAP read flag on a shared mailbox. Archive and move do sync, because they affect everyone.
- If a folder's UIDVALIDITY changes, re-sync that folder from scratch.

## Data model

Postgres holds the index, AI output and app state, managed with Drizzle. R2 holds raw email and attachments. Every table has an `org_id`. Login tables (users, sessions, organizations, members, invitations) come from Better Auth.

| Table | Key fields | Notes |
| --- | --- | --- |
| `mailboxes` | id, org\_id, address, kind, provider, credentials\_enc, status | `kind` is personal or shared. `provider` is purelymail now, gmail or microsoft later. Only the mail service can decrypt `credentials_enc`. |
| `mailbox_folders` | id, mailbox\_id, path, role, uidvalidity, highest\_modseq | `role` is inbox, sent, archive, trash or other. Holds each folder's sync position. |
| `mailbox_access` | mailbox\_id, member\_id, role | Who can see a mailbox. A personal mailbox has one owner. A shared one has many. |
| `threads` | id, org\_id, mailbox\_id, subject\_key, last\_message\_at, archived, triage, triage\_confidence, triage\_source, summary, summary\_message\_id | `triage_source` is ai or person. `summary_message_id` marks the last message the summary covers. |
| `messages` | id, org\_id, mailbox\_id, thread\_id, folder\_id, imap\_uid, message\_id\_header, in\_reply\_to, references, from, to, cc, sent\_at, r2\_key, clean\_text, search\_vector | Unique on (folder\_id, imap\_uid) and on (mailbox\_id, message\_id\_header). A missing Message-ID gets a hash of the headers instead. |
| `attachments` | id, message\_id, filename, mime\_type, size, r2\_key | Shown as chips under their message. |
| `thread_state` | thread\_id, member\_id, read, snoozed\_until | Per person, so a shared thread can be read for one person and unread for another. |
| `assignments` | thread\_id, member\_id, assigned\_at | Optional owner for shared-inbox threads. |
| `mail_actions` | id, org\_id, mailbox\_id, kind, payload, idempotency\_key, status, attempts, last\_error | The outbox. |
| `triage_feedback` | thread\_id, member\_id, from\_bucket, to\_bucket, created\_at | Every manual re-sort. Used to measure accuracy and tune thresholds. |
| `ai_usage` | org\_id, day, tokens\_in, tokens\_out | Enforces the daily AI cap. |
| `push_tokens` | member\_id, expo\_token, device | Where to send phone notifications. |

- A message sent to both rodrigo@ and hello@ is stored once per mailbox. That keeps access rules simple: you see a message if you can see its mailbox.
- Shared inboxes get one extra rule: the first person to reply or claim a thread becomes its assignee, and everyone else sees that.
- All reads go through one scoped helper, `db.forMember(memberId)`, which joins `mailbox_access`. Routes never query mail tables directly. Before SaaS, we add Postgres row-level security as a second lock.

## Threading and rendering

Threads look like a chat: one bubble per message, showing only what that person newly wrote. The hard part is cutting the quoted history, not drawing bubbles.

### Grouping messages into threads

1. If `In-Reply-To` or `References` matches a known `Message-ID`, join that thread.
2. Otherwise, if the message has no reply headers at all, match on normalized subject (strip Re:, Fwd:, RE:, AW:) plus overlapping participants within 30 days.
3. Otherwise, start a new thread.

Threading is a pure function in `mail-core`, tested against saved real emails.

### Cleaning each message

- mailparser turns raw MIME into text, HTML and attachments.
- mail-core's `stripReply` strips quoted history and signatures (ADR 0003). The result is `clean_text`. The original stays in R2.
- DOMPurify sanitizes HTML when the message is saved. Only sanitized HTML is ever sent to an app.

### Rendering rules

- Short messages render as bubbles. Long or formal ones (over about 120 words, or with tables) render as cards.
- Every bubble has a "show full message" toggle. Outlook's reply formatting will beat the parser sometimes.
- HTML renders in a sandboxed iframe with scripts off on web, and in a WebView with JavaScript off on iOS.
- Remote images are blocked by default to stop tracking pixels. When someone loads them, they come through our image proxy, so senders never see the reader's IP address.
- Forwards render as a quoted card inside the bubble, not as a new thread.
- People added to CC mid-thread get a small system line: "Ana added Luis."
- Attachments sit under their bubble as chips.

### Search

Postgres full-text search over subject, sender and `clean_text`, scoped by `db.forMember`. No extra service.

## AI

One provider, one model, one code path. The `ai` package exposes two functions, `triage()` and `summarize()`, built on the Anthropic SDK with Claude Haiku 5.5 and structured output. Both run in the queue consumer, never while a page is loading, so the inbox never waits on AI.

### Triage

- Input: sender, subject, `clean_text` of the latest message, thread length, whether we've replied before, and headers like List-Unsubscribe as signals.
- Output: one of `needs_reply`, `waiting_on_them`, `fyi`, `noise`, plus a confidence from 0 to 1.
- A thread whose latest message is from us is filed as `waiting_on_them` without calling the model.
- At 0.85 confidence or higher, file it automatically. Below that, show it in an "Unsure" lane for a person.
- A model's own confidence is not calibrated at first. We tune the 0.85 threshold from `triage_feedback` after the first few weeks.

### Summaries

- One to three sentences at the top of each thread: what's being asked, by whom, and any date or number that matters.
- Regenerate only when a new message arrives. Cache it in `threads.summary`.
- Skip summaries for threads triaged as noise.

### Safety and cost

- Email text is untrusted. The model has no tools and cannot act. Its output is shown as plain text, never HTML.
- Providers receive only the cleaned text needed for the job, never attachments.
- Each org has a daily token cap, tracked in `ai_usage`. Over the cap, summaries pause and triage keeps running.

## Clients and monorepo

```
omnidirectional/
  apps/
    web/        Vite + React SPA, TanStack Router + Query
    ios/        Expo (React Native)
    worker/     Hono API, AI queue consumer, realtime Durable Object; serves web/
    mail/       Node mail service: ImapFlow, Nodemailer, sync, outbox
  packages/
    db/         Drizzle schema, migrations, scoped queries (db.forMember)
    mail-core/  Pure functions: threading, reply stripping, sanitizing
    ai/         triage() and summarize() on the Anthropic SDK
    auth/       Better Auth config shared by worker, web and iOS
    ui/         Shared tokens and components
  fixtures/
    eml/        Real raw emails for tests (Gmail, Outlook, Apple Mail)
```

- **Web** ships first. Three panes: mailbox list with triage lanes, thread list, and the thread as chat.
- **iOS** follows once the web loop works. Same triage lanes, swipe to archive or snooze, push through Expo.
- **API client** comes from Hono RPC. Web and iOS import the types. No hand-written client to keep in sync.
- **Keep `mail-core` and `ai` free of UI and I/O code**, so they are easy to test and a Swift app could use the same API later.
- **Tests:** snapshot tests run `mail-core` against `fixtures/eml`. The mail service is tested against GreenMail, a local IMAP and SMTP test server in Docker.
- **Local dev:** Postgres in Docker, GreenMail in Docker, and `wrangler dev` for the Worker. No real mailbox needed.

## Security and credentials

The mail service holds a password for every mailbox, so a leak would expose everyone's email. These secrets get the same care as production database credentials.

- Use Purelymail app passwords, one per mailbox, never a person's real password. Each can be revoked alone.
- App passwords are encrypted with AES-256-GCM (standard tamper-proof encryption) before they reach Postgres. The key exists only in the mail service's secrets. Workers cannot decrypt them.
- The Purelymail API token also lives only in the mail service.
- Calls between the Worker and the mail service are signed (HMAC) and expire after a short window.
- Members sign in with passkeys or magic links through Better Auth. Web keeps the session in an httpOnly cookie (scripts can't read it). iOS keeps it in the phone's secure storage.
- Every mail query goes through `db.forMember`. Row-level security is added before any outside customer signs up.
- HTML is sanitized, rendered with scripts off, and images go through our proxy.
- Magic-link emails go out from a no-reply mailbox on Purelymail. This is transactional mail, which their terms allow.
- Backups: PlanetScale backs up Postgres. Purelymail holds the original mail, so the index can always be rebuilt.

## Path to SaaS

Already in place in v1: `org_id` on every table, Better Auth organizations, a `provider` column on mailboxes, and AI behind two functions.

What changes when we sell it:

- **Bring your own mailbox.** Customers will mostly use Gmail or Microsoft 365. At that point we evaluate EmailEngine, a self-hosted email API with a flat yearly license (roughly $1,000 to $1,500), instead of writing Gmail and Microsoft connectors ourselves.
- **Hosted mailboxes.** Only if Purelymail allows reselling. If not, we offer bring-your-own only.
- **More mail service instances.** Each instance takes a share of mailboxes by hash and holds their connections.
- **Database.** Move to a high-availability PlanetScale cluster and turn on row-level security.
- **Billing.** Stripe through Better Auth's Stripe plugin.
- **Data rights.** Per-org export and deletion.

## Considered and rejected

| Option | Why not, for now |
| --- | --- |
| Sieve copy of each email to a Cloudflare Email Worker | Depended on Cloudflare accepting redirected mail. Anyone who guessed the address could inject fake mail. We still needed IMAP for everything else. |
| Writing our own IMAP client inside Workers | Rebuilds a hard protocol from scratch. ImapFlow already does it well in Node. |
| Cloudflare D1 | The mail service can't reach it directly. Search and multi-tenancy are easier in Postgres. |
| Cloudflare Containers for the mail service | Built for work that sleeps between requests. We need connections open all day. |
| EmailEngine in v1 | Its license costs more than the rest of our infra combined. Revisit for Gmail and Microsoft support. |
| Jev for triage | Early access, and saves cents at our volume. Revisit once `triage_feedback` gives us a test set. |
| TanStack AI | Beta, and we use one provider. Revisit if we add a second. |
| TanStack Start with server rendering | The app is behind a login. Server rendering adds complexity with no gain. |
| Cloudflare Access for login | Doesn't work for customers or inside the iOS app. |
| S2 streams | Stores events but runs no code. Postgres and a Durable Object cover our needs. |
| Vercel eve | A framework for long-running agents. More than summaries need. Revisit for v2 "ask your inbox", alongside Cloudflare's Agents SDK. |

## Milestones

Each milestone ends with something usable. Dates are open until scope is confirmed.

1. **M0, plumbing proof.** Mail service on Fly.io with one Purelymail mailbox over IDLE. New mail lands in Postgres and R2. Done when a test email appears in under 5 seconds, and we know Purelymail's IDLE, CONDSTORE and connection limits.
2. **M1, read-only web inbox.** Login, threading, reply stripping, chat-style rendering, search, and full history import for all of Rodrigo's domains.
3. **M2, send and sync.** Outbox, reply, compose, Sent folder append, two-way read and archive, live updates.
4. **M3, AI.** Triage lanes with the Unsure lane, Haiku summaries, re-sort logging, daily caps.
5. **M4, shared inboxes.** Access roles, per-person read state, assignment.
6. **M5, iOS.** Expo app with push, triage lanes, swipe actions. Team switches over from Apple Mail.

## Risks and open questions

The biggest unknown is how Purelymail treats many long-lived IMAP connections. M0 exists to find out first.

| Risk | Why it matters | Fallback |
| --- | --- | --- |
| Purelymail limits open IMAP connections | One IDLE connection per mailbox could hit the limit. | IDLE only for active mailboxes. Poll the rest every minute with CONDSTORE. |
| Purelymail lacks CONDSTORE | Folder sync can't ask for only what changed. | Compare UID lists per folder. Fine at our mailbox sizes. |
| Mail service goes down | No new mail until it's back. | Fly.io restarts it. Sentry alerts us. On restart it resumes from each folder's saved sync position, so nothing is lost. |
| Reply parser misses Outlook quotes | Bubbles repeat old text. | "Show full message" toggle. Add failing emails to `fixtures/eml` and fix the rule. |
| Triage confidence is off | Threads get filed in the wrong lane. | The Unsure lane catches doubt. Tune the threshold from re-sort data. |
| Purelymail is a small company | An outage means no mail. | Mail stays standard IMAP. Moving hosts is a DNS change plus a copy. |

**Open questions**

- [ ] Do summaries and triage run on shared inboxes for everyone, or only for the assignee?
- [ ] Does Purelymail allow reselling hosted mailboxes? Ask them before planning hosted SaaS plans.
- [ ] Which domain hosts the app: `omnidirectional.app`, or a shorter one?
